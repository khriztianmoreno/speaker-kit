# Development guide

This guide is for developers working **on** `@khriztianmoreno/speaker-kit` — cloning the repo, iterating on the source, testing changes against a real Next.js app, and cutting a release. If you only want to **use** the package in your own project, see the [`README.md`](./README.md).

---

## 1. Prerequisites

| Tool | Recommended version | Notes |
|---|---|---|
| Node.js | `>= 18.18` (LTS 20 ideal) | Required by `tsup` and by Next.js 14+ in the test app. |
| pnpm | `>= 9` | The repo ships a `pnpm-lock.yaml`. Other package managers work, but the lockfile won't regenerate identically. |
| Git | any recent | — |

> If you use `nvm`: `nvm use --lts` before installing.

---

## 2. Clone and install

```bash
git clone git@github.com:khriztianmoreno/speaker-kit.git
cd speaker-kit
pnpm install
```

`pnpm install` pulls in everything declared as `peerDependencies` via `devDependencies` (`react`, `react-dom`, `@supabase/supabase-js`, `@types/*`), so the package builds and typechecks in isolation without needing a consumer app.

---

## 3. Project layout

```
speaker-kit/
├── src/
│   ├── components/        # SpeakerView, AudienceView, SlidePreview, Splitter, Timer
│   ├── hooks/             # useSlideSync, useElapsed, useWallClock, useLayoutPersistence
│   ├── transports/        # BroadcastChannelTransport, SupabaseTransport
│   ├── styles/
│   │   └── speaker-kit.css
│   ├── icons.tsx
│   ├── types.ts
│   └── index.ts           # Public entry point — every public export goes here
├── dist/                  # Generated by tsup (gitignored)
├── tsup.config.ts         # Build config (ESM + CJS + d.ts + copies styles.css)
├── tsconfig.json
└── package.json
```

House rules:

- Anything public must be re-exported from `src/index.ts`.
- Any component or hook that touches the DOM or runs timers must start with `"use client"` — required for the Next.js App Router consumers.
- `react`, `react-dom`, `next`, and `@supabase/supabase-js` are **peer dependencies** and listed as `external` in `tsup.config.ts`. Do **not** move them to `dependencies`.

## 4. Scripts

Defined in `package.json`:

| Command | What it does |
|---|---|
| `pnpm build` | Builds ESM + CJS + `.d.ts` into `dist/`, then copies `speaker-kit.css` to `dist/styles.css`. |
| `pnpm dev` | Same as `build` but in watch mode (`tsup --watch`). Use while iterating. |
| `pnpm typecheck` | Runs `tsc --noEmit`. Strict mode is on, so implicit `any` fails. |
| `pnpm release` | `build` + `npm publish --access public`. Maintainer only (see §8). |

## 5. The peer-dep duplication footgun

Before describing the dev loop: there is **one gotcha** that bit us during development and that you'll hit if you use `pnpm link` or `file:` protocol naively.

### The symptom

You link the package into a consumer Next.js app and run `pnpm typecheck` in the consumer. You get errors like:

```
Type 'React.FunctionComponent<{}>' is not assignable to type
'import("/Users/.../speaker-kit/node_modules/.pnpm/@types+react@18.3.31/.../index").FunctionComponent<{}>'.
  Type 'bigint' is not assignable to type 'ReactNode'.
```

Notice the path: TypeScript is comparing your consumer's `@types/react` against **a second copy of `@types/react`** that lives inside `speaker-kit/node_modules`.

### Why it happens

`pnpm link` and `pnpm add file:../speaker-kit` both create a **symlink** from the consumer's `node_modules/@khriztianmoreno/speaker-kit` to the source repo. TypeScript follows the symlink and finds the nested `node_modules` we use to build the package — which contains its own copy of every peer dep, often a slightly different patch version. To TypeScript, two `.d.ts` files at two paths are two different types, even if their contents match byte-for-byte.

This **only affects TypeScript**. At runtime, Webpack/SWC resolve the imports correctly and everything works.

### The fix: install from a tarball

The clean workaround — and the one we use — is to install via `pnpm pack`. The tarball install copies the package into pnpm's content-addressable store, so the symlink terminates there instead of in the source tree. No nested `node_modules` are reachable from the consumer.

See §6 for the workflow.

## 6. Local dev loop

Pick the option that matches your goal.

### 6.1 Iterating on the package alone

If you just want to write code and let `tsc` / `tsup` catch problems, you don't need a consumer at all:

```bash
pnpm dev          # tsup --watch — rebuilds dist/ on save
pnpm typecheck    # in another terminal, before commits
```

### 6.2 Testing against a real Next.js app — the reliable way

This is the path that **works without TypeScript breaking**:

```bash
# Terminal 1 — inside speaker-kit
pnpm build && pnpm pack
# → produces khriztianmoreno-speaker-kit-1.0.0.tgz

# Terminal 2 — inside your consumer app
pnpm add /absolute/path/to/speaker-kit/khriztianmoreno-speaker-kit-1.0.0.tgz
```

That writes a `file:` entry in the consumer's `package.json` pointing at the tarball, e.g.:

```json
"@khriztianmoreno/speaker-kit": "file:/Users/you/dev/speaker-kit/khriztianmoreno-speaker-kit-1.0.0.tgz"
```

Now the consumer typechecks cleanly and uses your local build.

**Every time you change the package**, repeat:

```bash
cd speaker-kit
pnpm build && pnpm pack

cd ../your-app
pnpm install   # picks up the new tarball
```

Slower than a live link, but it's the closest thing to "install from npm" without actually publishing — and it sidesteps §5 entirely.

> Tip: alias the cycle in your shell, e.g. `alias sk-rebuild='cd ~/dev/speaker-kit && pnpm build && pnpm pack && cd - && pnpm install'`.

### 6.3 `pnpm link` (fast, but watch out)

If you accept the §5 caveat and don't care about consumer typecheck noise (e.g. you only want to verify the UI), `pnpm link` is faster:

```bash
# Register globally
cd speaker-kit
pnpm link --global

# Connect from your app
cd ../your-app
pnpm link --global @khriztianmoreno/speaker-kit
```

When done:

```bash
cd ../your-app
pnpm unlink --global @khriztianmoreno/speaker-kit
pnpm install   # restore the published / tarball version
```

### 6.4 Smoke test in a consumer

Once the package is installed, a minimal page:

```tsx
// app/slides/page.tsx
"use client";
import { SpeakerView } from "@khriztianmoreno/speaker-kit";
import "@khriztianmoreno/speaker-kit/styles.css";

const SLIDES = [
  { id: "a", Component: () => <h1>Slide A</h1>, title: "A" },
  { id: "b", Component: () => <h1>Slide B</h1>, title: "B" },
];

export default function Page() {
  return <SpeakerView slides={SLIDES} channel="dev-test" />;
}
```

Without `supabase`, sync only works between tabs in the same browser (via `BroadcastChannel`). For cross-device, see §7.

> **Next.js cache:** if changes to the package don't show up after a rebuild, restart `next dev`. Webpack/Turbopack sometimes caches the previous `dist/`. `rm -rf .next` clears it if needed.

## 7. Testing Supabase Realtime sync

Cross-device sync uses **Supabase Realtime broadcast**, so you need a project at [supabase.com](https://supabase.com) (free tier is plenty).

1. Create a project and copy `Project URL` + `anon key` from *Settings → API*.
2. In the **consumer app** (not this repo), add a client:

   ```ts
   // lib/supabase.ts
   import { createClient } from "@supabase/supabase-js";

   export const supabase = createClient(
     process.env.NEXT_PUBLIC_SUPABASE_URL!,
     process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
   );
   ```

3. Pass it to `SpeakerView` / `AudienceView` via the `supabase` prop.
4. Open `/slides/speaker` on one device and `/slides` on another. They should stay in sync.

> **Footgun:** if you run `pnpm dev` locally **and** keep a production build open using the same `channel`, you'll drive prod from localhost. Use a distinct `channel` in `.env.local`, or close prod while developing.

## 8. Typechecking and styles

- Run `pnpm typecheck` before every commit. Strict mode is on.
- CSS lives in `src/styles/speaker-kit.css` and `tsup` copies it to `dist/styles.css` on each build (see the `onSuccess` hook in `tsup.config.ts`).
- Never edit files under `dist/` — they're regenerated and `clean: true` deletes them every build.
- If you add a new class to a component, add it to the stylesheet too. Stick to CSS variables (`--sk-*`) so consumers can theme without overriding selectors.

## 9. Release process (maintainer only)

1. Make sure `main` is clean and green:
   ```bash
   pnpm typecheck
   pnpm build
   ```
2. Bump the version following strict SemVer. Since we ship `1.x` (not `0.x`), every **breaking change** is a major bump:
   ```bash
   npm version patch   # bug fix
   npm version minor   # new feature, additive
   npm version major   # breaking API change
   ```
   This creates a `v1.x.y` commit and a git tag.
3. Push commit + tag:
   ```bash
   git push --follow-tags
   ```
4. Publish:
   ```bash
   pnpm release
   ```
   This runs `pnpm build && npm publish --access public`. You need to be logged in (`npm login`) and have access to the `@khriztianmoreno` scope.

After publish, anyone consuming via the local tarball should switch to the registry version:

```json
// before (local dev)
"@khriztianmoreno/speaker-kit": "file:/.../khriztianmoreno-speaker-kit-1.0.0.tgz"

// after (npm)
"@khriztianmoreno/speaker-kit": "^1.0.0"
```

> The `files` field in `package.json` ships `dist/`, `README.md`, and `LICENSE` — nothing else. If you add something the consumer needs (e.g. a second stylesheet), update `exports` and the copy step in `tsup.config.ts`.

## 10. Conventions

- Branches: `feat/<short-description>`, `fix/<short-description>`, `chore/<...>`.
- Commit messages: Conventional Commits — `feat: add foo`, `fix(speaker): handle empty slides`, `docs: clarify channel prop`. Makes the changelog easy.
- One PR = one logical change. Attach before/after screenshots for UI changes.

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| TS errors comparing two `@types/react` paths in the consumer | `pnpm link` / `file:` symlink — see §5 | Switch to `pnpm pack` + tarball install (§6.2). |
| `Module not found: Can't resolve "react"` when the consumer builds | The app doesn't declare `react` as a dep | `react` is a peer dep — install it in the consumer. |
| Changes in `src/` don't show up in the linked app | `next dev` cache | Restart `next dev`. `rm -rf .next` if it persists. |
| `BroadcastChannel is not defined` in server logs | A client component is being rendered during SSR | Make sure the file starts with `"use client"`. Built-in components already do. |
| `pnpm release` fails with 403 | Not logged in to npm or no access to the scope | `npm whoami` / `npm login`; verify access to `@khriztianmoreno`. |
| `dist/styles.css` missing after build | The `onSuccess` step in `tsup.config.ts` failed | Confirm `src/styles/speaker-kit.css` exists and rerun `pnpm build`. |
| Old types showing in consumer after rebuild | Tarball name didn't change (`1.0.0`), pnpm cached it | Either bump the version, or `pnpm store prune` and reinstall. |

## 12. Adding features — where things go

| Goal | Where to add it | Don't forget |
|---|---|---|
| New public component | `src/components/` | Export from `src/index.ts`, document in `README.md`. |
| New public hook | `src/hooks/` | Export from `src/index.ts`. Add `"use client"` if it touches DOM/timers. |
| New transport | `src/transports/`, implement `Transport` | Export from `src/index.ts`. Show usage with the `transports` factory in `useSlideSync`. |
| Change wire format | `src/types.ts` (`SyncMsg` / `NavMsg` / `ReqStateMsg`) | **Breaking change** — bump major. Connected clients on different versions will desync. |
| New CSS hook | `src/styles/speaker-kit.css` | Prefer `--sk-*` CSS variables over hard-coded colors so consumers can theme. |
